# ADR-001: Базовая архитектура приложения

**Статус:** Предложен

**Дата:** 2026-08-05

## Контекст

Проект "Morning Companion" развивается от простого бота до многофункционального ассистента. Для обеспечения долгосрочной стабильности, расширяемости и удобства сопровождения необходимо заложить надежный архитектурный фундамент. Текущий подход с размещением логики в `main.py` и связанных модулях не масштабируется и приводит к сильной связанности компонентов (high coupling).

Требуется архитектура, которая:
- Четко разделяет зоны ответственности (Separation of Concerns).
- Легко тестируется.
- Позволяет заменять или обновлять отдельные части системы (например, провайдера ИИ или СУБД) с минимальными изменениями в бизнес-логике.
- Понятна для новых участников команды.

## Решение

Мы принимаем за основу принципы **Чистой Архитектуры (Clean Architecture)**, адаптированные для асинхронного Python-приложения.

Ключевые паттерны и компоненты:

1.  **Слоистая структура:**
    - **`Domain Layer` (домен):** Модели данных (Pydantic/SQLAlchemy) и бизнес-сущности. Не зависит ни от чего.
    - **`Application Layer` (приложение):** Сервисы (`Services`), содержащие бизнес-логику. Оркестрируют работу с репозиториями и внешними системами. Зависят только от домена.
    - **`Infrastructure Layer` (инфраструктура):** Реализация внешних зависимостей: работа с базой данных (репозитории), Telegram API, провайдеры ИИ, брокеры сообщений. Зависит от слоя приложения (реализует его интерфейсы).

2.  **Dependency Injection (DI):** Мы будем использовать DI для управления зависимостями между компонентами. Это позволит нам легко подменять реализации в тестах (например, мокать репозиторий) и сделает связи между частями системы явными.

3.  **Service Layer (`app/services`):** Каждый сервис инкапсулирует определенный набор бизнес-операций (use case). Например, `DialogService` будет отвечать за обработку диалогов, а `UserService` — за управление пользователями. Сервисы не должны напрямую зависеть от конкретных фреймворков (FastAPI, aio-pika и т.д.).

4.  **Repository Pattern (`app/repositories`):** Этот паттерн абстрагирует слой доступа к данным. Для каждой доменной модели будет создан репозиторий (например, `UserRepository`), который предоставляет CRUD-интерфейс (`get`, `create`, `update`). Бизнес-логика в сервисах будет работать с репозиторием, не зная, какая СУБД используется под капотом (PostgreSQL, SQLite). Реализация будет построена на SQLAlchemy.

5.  **Абстракция AI Provider (`app/ai`):** Вместо прямого использования конкретной библиотеки для работы с ИИ, мы создадим интерфейс `AIProvider`, который будет реализовываться конкретными классами (`OpenAIProvider`, `GeminiProvider`). Это позволит в будущем легко переключаться между моделями или даже использовать несколько одновременно.

6.  **Точка входа и запуск (`app/main.py`, `app/core`):** `main.py` станет минималистичным. Вся логика по созданию и конфигурации приложения (`Application`), инициализации модулей (СУБД, бот, планировщик) будет вынесена в `app/core/application.py` и `app/core/lifecycle.py`. Это реализует предложенный "Bootstrap" процесс.

## Последствия

### Плюсы

- **Тестируемость:** Компоненты легко изолировать и тестировать благодаря DI и четким границам.
- **Масштабируемость:** Новые функции можно добавлять, создавая новые сервисы и репозитории, не затрагивая существующий код.
- **Гибкость:** Легко заменить СУБД, Telegram-фреймворк или модель ИИ.
- **Порядок:** Структура проекта становится предсказуемой и самодокументируемой.

### Минусы

- **Больше кода:** Для простых функций требуется создать больше файлов и классов (сервис, интерфейс репозитория, реализация).
- **Выше порог входа:** Новым разработчикам может потребоваться время, чтобы понять архитектурные паттерны.
